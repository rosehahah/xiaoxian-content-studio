## 图2：Tag 找到代码，Release 交代这一版。

先分清 · 两个功能各有用处

GitHub 仓库，就是存放项目代码和修改记录的地方。

**Tag｜版本标签**

给某一次代码提交起个名字，例如 v0.1.0。
“提交”就是 Git 记录的一次代码保存。
Tag 指向这次记录，方便以后定位。

**Release｜版本说明页**

基于一个 Tag，写下变化、使用方法和已知问题。
GitHub 提供对应源码下载；你也可以另外上传打包好的文件。

Release 本身不等于网站上线；是否触发部署取决于项目配置。

README 是项目里的使用说明。上面的验证结果是示例；实际没有测试过的项目，就写“未验证”。

版本号是示例。附件可选；生成可用安装包需要另外打包。

## 图4：第一次，照着这条路走。

网页版操作 · 代码先保存到 GitHub

前提：代码已上传 GitHub，你有仓库写权限。

确认目标分支的最新提交，就是要保留的版本；记下提交编号。
进仓库 Releases → Draft a new release。
Choose a tag：创建未占用的名字，如 v0.1.0；Target 选已检查的分支。
填版本标题与说明；暂不确定时，先点 Save draft。
核对目标与说明后，再由你点 Publish release。

分支是一条修改路线。保存草稿不等于发布完成；发布后继续核对。

## 图5：看到版本号，还不算检查完成。

验收 · 发布 Release 后再检查

不是“有个标签”就够了，要确认它确实对应想保留的代码。

**至少确认这三件事**

在 Releases / Tags 中能找到版本；Tag 对应的提交编号与记录一致。
Release 说明写清变化、使用方法与限制，没有把未测功能写成已验证。
从该 Release 的 Assets 下载 Source code (zip)，放进新文件夹，按 README 验证关键功能。

**如果取回来跑不起来**

先记录缺少的环境、依赖或配置，再补使用说明。不要把下载成功当成恢复成功。

本地创建的 Tag 还要推送到 GitHub；修正代码用新版本号，别覆盖旧 Tag。

先检查清单和目标代码，再决定后续操作。

## 图7：留住一个版本，还要知道它的边界。

最后分清 · 避免三个常见误会

下一次要改项目时，你需要的是能定位、能解释、能验证的版本记录。

**容易混淆的地方**

源码 ZIP = 安装包？ | 它是代码快照，通常还需按 README 配好环境和依赖。
Tag = 所有数据的备份？ | 未提交文件、外部数据库和密钥不会自动包含。
取回旧代码 = 网站恢复？ | 取回与部署是两件事，线上回滚还需单独处理。

先保留好用版本的提交记录，再继续改。示例与操作依据见随附来源。
